# WhatsApp CLI (wacli) — Setup and Auth

Use when the client asks to connect their WhatsApp Business account so you can read/send/monitor messages. Covers QR pairing and phone-number pairing, including common protocol failures.

## Installation

The binary should already be installed at `/usr/local/bin/wacli`. If not:

1. Install Go: `apt-get install -y golang-go` (needs Go 1.25+, auto-downloads toolchain but needs ~400MB disk for Go cache)
2. `go install github.com/openclaw/wacli/cmd/wacli@latest`
3. Binary lands at `~/go/bin/wacli` or `/usr/local/bin/wacli` if `GOBIN=/usr/local/bin`

Verify: `wacli version` (current: 0.11.1, latest as of June 2026)

## Full Auth Flow

### Step 1: Clean Slate (if retrying)

If auth has been attempted before and failed, remove stale state:

```
wacli accounts remove <name>
rm -rf /root/.local/state/wacli/
```

### Step 2: Create Account

```
timeout 5 wacli accounts add creed
```

This blocks because it starts the QR auth flow. The `timeout 5` kills it early but the account config file is already written. Verify with `wacli accounts list`.

Alternative: start `wacli accounts add creed` in a background process, wait 4s for the config file, then proceed.

### Step 3A: QR Auth (Preferred for in-person or image-capable channels)

```
wacli auth --account creed --qr-format text
```

This outputs the raw pairing data as text (a comma-separated string). Capture it and immediately generate a PNG:

```
qrencode -o /tmp/whatsapp-qr.png -s 8 -m 3 "<pairing-data>"
```

Then send the PNG to the client with:

> "Open WhatsApp → **Linked Devices** → **Link a Device** → Scan this QR code"

**IMPORTANT**: The `wacli auth` process MUST stay running while the client scans. If it exits, the QR expires. Run in a background `terminal()` call so it stays alive, then send the QR image via `send_message` with `MEDIA:` path.

### Step 3B: Phone Number Pairing (More Reliable)

When QR codes keep failing, use the phone number method:

```
wacli auth --account creed --phone "+44 7XXX XXXXXX"
```

This generates a **pairing code** (format: `8P3Z-A6Y3`). The client enters this code on their phone:

> WhatsApp → **Linked Devices** → **Link a Device** → **Link with phone number** → Enter code: `XXXX-XXXX`

**CRITICAL**: The auth process MUST stay running while the client enters the code. If killed, the code is invalidated. The process waits ~60s by default.

### Step 4: Verify Connection

Once authenticated:
- Check status: `wacli auth status --account creed`
- List chats: `wacli chats list --account creed --limit 10`
- Full sync: `wacli sync --account creed --follow`

## Known Protocol Failures

### "missing <link_code_pairing_wrapped_primary_ephemeral_pub> element in notification"

This is a **whatsmeow protocol mismatch**. The underlying Go library doesn't understand the response WhatsApp's server sent during pairing. Happens when Meta updates their pairing protocol faster than the library.

**What to try (in order):**

1. **Clean slate + retry** — `wacli accounts remove creed` + `rm -rf /root/.local/state/wacli/` + start fresh. Sometimes transient.
2. **Switch between QR and phone method** — if QR fails, try `--phone` and vice versa. Different code paths may work.
3. **Update wacli** — `go install github.com/openclaw/wacli/cmd/wacli@latest` (though v0.11.1 was the latest as of June 2026)
4. **Try a different code** — the protocol error sometimes resolves on retry (wacli auto-retries 3 times)

### QR Code "Not Liked" / "Code Incorrect"

Possible causes:
- The auth process died before the client scanned (QR codes expire when the process exits — about 20s after start)
- QR image generated by `qrencode` was too small or poor quality (use `-s 8 -m 3` minimum, 500+ px)
- WhatsApp rejected the pairing from a data-centre IP
- A previous stale session is still registered as a linked device (force client to remove old session from WhatsApp settings)

### Phone "Code Incorrect" vs Actual Rate Limiting

The user may say "code incorrect" but the actual error could be rate limiting. These sound the same to the user but require different fixes. **When the user says the code was "incorrect", it's almost always rate limiting, not an actual code error.**

**What actually happens:** `--phone` auth succeeds in generating a pairing code. The user enters it on their phone. WhatsApp's server responds with 429 (rate-overlimit). The CLI shows "pair phone: info query returned status 429" — but the user never sees this because the session dies before they report back. They only know the code "didn't work."

| User Says | Likely Root Cause | Fix |
|-----------|-------------------|-----|
| "Code incorrect" | Rate limiting (429) | Wait 30min-2h for cooldown |
| "Code doesn't work" | Process died / code expired | Start fresh, keep process alive |
| "QR doesn't scan" | Image too small or stale | Regenerate with `-s 8 -m 3` minimum |
| "QR not liked" | WhatsApp rejected server IP | Try `--phone` method or different network |

**Practical session note (July 2026):** Ibrahim's phone pairing succeeded on the 4th attempt after a ~30 min cooldown. The codes generated BEFORE the rate limit kicked in ("JKVY-624E", "FAXK-H2BW", "8V3C-4DWH") were actually valid — each retried automatically (3 attempts built into wacli) but kept hitting 429. The final pairing code ("YGFZ-88H6") worked after the bank of 3 automatic retries exhausted, then a fresh `tmux new-session` attempt. The key lesson: **keep trying every 30-60 min, wipe state between attempts, use tmux to keep the process alive without output buffering issues.**

### Rate Limiting (Status 429)

WhatsApp rate-limits pairing attempts when you try too many times in quick succession:

```
pair phone: info query returned status 429: rate-overlimit
```

**What to do:**
- Wait 30 minutes minimum (could be up to 2 hours for full cooldown)
- Wipe state before retrying: `wacli accounts remove creed && rm -rf /root/.local/state/wacli/`
- Then create fresh: `timeout 6 wacli accounts add creed`
- Then auth: `wacli auth --account creed --phone "+44..."`

**Prevention:**
- Don't generate more than 2-3 codes per hour
- Each failed attempt counts toward the rate limit
- The limit is per-IP, not per account

### "auth connection dropped before pairing completed" (retry loop)

wacli automatically retries 3 times. If all 3 fail:
- Try `--phone` method instead of QR
- Try from a different network/VPS
- Remove the WhatsApp Business session from the phone's Linked Devices first

## WhatsApp Web / whatsapp-web.js (Browser Approach — AVOID)

Do NOT use browser-based WhatsApp Web approaches on a headless VPS:

- `web.whatsapp.com` is too heavy for headless browser tools (times out)
- `whatsapp-web.js` requires Puppeteer/Chrome which is ~300MB+ and often fails on headless VPS
- The browser tool's headless engine can't handle WhatsApp Web's JS load

Stick with wacli for all WhatsApp operations.

### QR via `--qr-format text` (Bypass terminal issues)

When `wacli auth` in a terminal session produces no output or times out before the QR generates, use `--qr-format text` with a short timeout to capture the raw pairing data:

```bash
timeout 15 wacli auth --qr-format text 2>&1
```

This outputs the pairing data as a comma-separated string (not an ASCII QR grid). Capture that string and pipe to qrencode or Python's qrcode library:

```bash
qrencode -o /tmp/qr.png -s 10 -m 3 "<pairing-data>"
```
```python
import qrcode
qr = qrcode.QRCode(box_size=10, border=4)
qr.add_data("<pairing-data>")
qr.make(fit=True)
img = qr.make_image(fill_color="black", back_color="white")
img.save("/tmp/whatsapp_qr.png")
```

**Why this works:** `--qr-format text` outputs the underlying data immediately. The `timeout 15` kills the process quickly. For the actual scan, you need the process to stay alive — but for generating the QR image to send to the user, `--qr-format text` + qrencode/qrcode is the correct flow.

**Send via send_message:** Include MEDIA:/tmp/qr.png in the message text. The image goes as a native photo on Telegram.

## Process Lifecycle Management

**Foreground pattern** (recommended for phone pairing):
```
timeout 120 wacli auth --account creed --phone "+447..." --timeout 2m
```
Keep this running, send the code, wait for user confirmation.

**Background pattern** (for QR):
1. Start `stdbuf -oL wacli auth --account creed --qr-format text` in `terminal(background=true)` (use `stdbuf -oL` to prevent pipe buffering from delaying output visibility)
2. Watch for the pairing data output via `process(action='poll')`
3. Generate QR image with qrencode
4. Send to client
5. Process stays alive in background until scanned or timeout

**Python subprocess pattern** (when Fine-Grained Control is needed):
```python
import subprocess, time, re
p = subprocess.Popen(['wacli', 'auth', '--account', 'creed', '--phone', '+447...'],
    stdout=subprocess.PIPE, stderr=subprocess.STDOUT, text=True, bufsize=1)
code = None
while time.time() - start < 20:
    line = p.stdout.readline()
    if 'Pairing code' in line:
        m = re.search(r'([A-Z0-9]{4}-[A-Z0-9]{4})', line)
        if m: code = m.group(1); break
# Show code to user, then:
p.wait(timeout=90)  # keep alive for scan
```

## Pitfalls

- **NEVER use shell `&` for backgrounding** — the terminal tool rejects it. Use `terminal(background=true)` or Python subprocess.
- **Account must exist before auth.** `accounts add creed` first, then `auth --account creed`. Running `auth` on a non-existent account gives: `account config not found; run wacli accounts add creed`.
- **QR data is single-use and expires with the process.** Generate the image AFTER starting the auth listener, not before.
- **Phone code expires after ~60s.** Tell the client to have WhatsApp open and ready before generating the code.
- **No home channel for send_message.** After the daily reset, wacli's linked-device session is lost. Must re-auth.
- **The wacli tmux session process should be kept alive** after linking so `wacli send text` commands work. The authentication itself persists across vm restarts (session.db stores credentials). If the linked-device session disconnects from WhatsApp's end, the user will see "Your linked session was removed" and you need to re-auth.
- **wacli v0.11.1 is the latest** as of June 2026. No newer version available. If pairing fails, it's a server-side protocol issue, not a stale binary.

## Integration with Monitoring Workflow

Once authenticated, to monitor messages continuously:

```
wacli sync --account creed --follow
```

This streams new messages as they arrive. In a background terminal session, pipe output to a log file. For checking specific messages:

```
wacli messages search --account creed --limit 20 "keyword"
wacli chats list --account creed --limit 10
```
